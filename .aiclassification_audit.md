## 🔴 CRITICAL ISSUES FOUND

### 1. **Tooltip Inaccuracies - Strategy Type Time Ranges**

**Location**: `dashboard/src/components/dashboard/AccountSummaryCard.tsx:74` + `BehavioralPatternsTab.tsx:418`

**Issue**: Documented time ranges don't match actual implementation

**Current Tooltips Say:**
- `FAST_TRADER`: "holds < 1 hour"  
- `DAY_TRADER`: "4-24 hours"

**Actual Code Logic** (analyzer.ts:1649-1653):
```typescript
if (speedCategory === 'SNIPER' || speedCategory === 'SCALPER' || speedCategory === 'MOMENTUM') {
  return 'FAST_TRADER'; // MOMENTUM is 5-30min, not < 1h
}
if (speedCategory === 'INTRADAY' || speedCategory === 'DAY_TRADER') {
  return 'DAY_TRADER'; // INTRADAY is 30min-4h, DAY_TRADER is 4-24h
}
```

**Speed Category Actual Ranges** (constants.ts:276-282):
- SNIPER: < 1 min
- SCALPER: 1-5 min  
- MOMENTUM: 5-30 min (0.5 hours)
- INTRADAY: 30min-4h
- DAY_TRADER: 4-24h

**Correct Descriptions Should Be:**
- `FAST_TRADER`: "< 30 minutes" (includes SNIPER, SCALPER, MOMENTUM)
- `DAY_TRADER`: "30 minutes to 24 hours" (includes INTRADAY, DAY_TRADER speed categories)

**Impact**: Users filtering for FAST_TRADER expect < 1h but might get 30min holders. Users filtering DAY_TRADER expect 4-24h but get 30min-4h traders.

**Fix Required**: Update tooltip text in both components.

## 🟡 DESIGN DECISIONS TO VERIFY

### 3. **Flow-Dominant Strategy Override**

**Location**: `analyzer.ts:1638-1640`

**Behavior**: ACCUMULATOR and DISTRIBUTOR flow patterns override speed-based classification

**Example Scenario:**
- Wallet: 50 tokens, 3-day median hold (SWING speed), 30 buys / 6 sells (5:1 ratio)
- Flow: ACCUMULATOR (ratio >= 2.0)
- Speed: SWING (3 days)
- **Result**: strategyType = 'ACCUMULATOR' (NOT 'SWING_TRADER')

**Consequence**: Users filtering for "SWING_TRADER" will NOT see swing traders who accumulate.

**Question for User**: Is this intentional? Should flow always override speed?

**Alternative Design**: Could introduce composite types like "SWING_ACCUMULATOR" or use multi-tag filtering.

---

### 4. **Holder Bypass Strictness**

**Location**: `analyzer.ts:1619-1623, constants.ts:354-361`

**Current Thresholds:**
- Multi-token bypass: 3+ tokens held 24+ hours
- Single-token bypass: 1 token worth 50+ SOL

**Edge Case Example:**
- Wallet: 2 tokens, held 48 hours each, worth 40 SOL each (80 SOL total)
- **Result**: Fails both bypasses → classified as 'LOW_ACTIVITY'

**Question**: Is 50 SOL threshold too high? A wallet with 80 SOL in holdings getting "low activity" seems harsh.

**Suggestion**: Consider lowering to 25-30 SOL, or use total holdings value instead of single largest position.

---

### 5. **MIXED Flow Pattern Edge Case**

**Location**: `analyzer.ts:1643-1646`

**Scenario**: Wallet passes holder bypass (has holdings) but has MIXED flow pattern

```typescript
if (speedCategory === null) {
  if (flowPattern === 'BALANCED') return 'BALANCED_TRADER';
  return 'LOW_ACTIVITY'; // ← MIXED flow lands here
}
```

**Example:**
- 4 tokens held (passes multi-token bypass)
- Buy/sell ratio: 1.5 (neither BALANCED nor ACCUMULATOR)
- No completed cycles yet (speedCategory = null)
- **Result**: 'LOW_ACTIVITY' despite having meaningful holdings

**Question**: Should wallets with holdings ever be marked LOW_ACTIVITY?
