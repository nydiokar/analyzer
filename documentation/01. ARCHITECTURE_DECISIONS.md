# 🏗️ Architecture Decisions & Technical Trade-offs

## 🎯 Document Purpose

This document captures the **key architectural decisions** made during the development of the Wallet Analysis System, explaining **why** certain choices were made and what **trade-offs** were considered. This helps future developers understand the reasoning behind the current system design.

## 🚀 Core Architecture Principles

### **1. Service-Oriented Architecture**
- **Decision**: Separate core analysis logic from API and presentation layers
- **Why**: Enables reuse across CLI scripts, API endpoints, and background workers
- **Trade-offs**: 
  - ✅ **Pros**: Modular, testable, maintainable
  - ❌ **Cons**: More initial setup, potential for over-engineering

### **2. TypeScript-First Development**
- **Decision**: Use TypeScript throughout the entire stack
- **Why**: Type safety, better IDE support, reduced runtime errors
- **Trade-offs**:
  - ✅ **Pros**: Compile-time error catching, better refactoring
  - ❌ **Cons**: Build complexity, learning curve for some developers

### **3. Database-First Design**
- **Decision**: Design database schema first, then build services around it
- **Why**: Ensures data integrity and enables efficient querying
- **Trade-offs**:
  - ✅ **Pros**: Consistent data model, optimized queries
  - ❌ **Cons**: Schema changes require migrations, upfront design time


## 🔐 Authentication & Authorization Architecture

### **Composite Authentication Strategy** (Updated 2025-12-03)
- **Decision**: Implement dual authentication system (JWT for humans + API Keys for services)
- **Why**:
  - **Separation of Concerns**: Identity (JWT) vs Permissions (API keys)
  - Support modern JWT-based user authentication for dashboard/browser users
  - Maintain backward compatibility with existing API key integrations
  - Enable fine-grained access control via API key scopes (`read`, `report`, `analysis`, `admin`, `full`)
  - Services (Prometheus, CI/CD) use API keys with scopes, not JWT
- **Implementation**:
  - Global `CompositeAuthGuard` tries JWT first, falls back to API key
  - JWT contains ONLY identity (`sub`, `email`) - NO scopes (intentional design decision)
  - API keys contain scopes for permission checks (`ApiKeyService.hasScope()`)
  - Single guard handles both authentication methods transparently
  - On registration: API key created internally (hashed, not returned) for backward compatibility
- **Why JWT Has No Scopes** (Critical Design Decision):
  1. **Instant Revocation**: AdminGuard checks `ADMIN_USER_IDS` env var → change env + restart = immediate access removal (no token refresh needed)
  2. **Simplicity**: No scope management UI, no "update scopes → force logout" flow
  3. **Smaller Payload**: JWT stays lightweight, faster transmission
  4. **Separation of Concerns**: Humans use identity-based auth, services use permission-based auth
  5. **No Privilege Escalation Risk**: Can't embed admin scope in long-lived token
- **Trade-offs**:
  - ✅ **Pros**: Seamless migration path, supports multiple client types, clear separation (identity vs permissions), instant admin revocation
  - ❌ **Cons**: Increased complexity in auth logic, two authentication systems to maintain
- **Use Cases**:
  - JWT: Human users via browser/Postman, admin checks via `ADMIN_USER_IDS`
  - API Keys: Prometheus scraping (`admin` scope), CI/CD pipelines (`read` scope), external integrations

### **Global Guard Pattern**
- **Decision**: Use global authentication guard at application level
- **Why**:
  - **Security by Default**: All routes protected unless explicitly marked `@Public()`
  - **DRY Principle**: Avoid repeating `@UseGuards()` on every controller
  - **Fail-Safe**: New endpoints are automatically protected
- **Implementation**:
  ```typescript
  // app.module.ts
  providers: [
    { provide: APP_GUARD, useClass: CompositeAuthGuard },  // Auth
    { provide: APP_GUARD, useClass: ThrottlerGuard },      // Rate limiting
    { provide: APP_GUARD, useClass: AdminGuard },          // Admin checks
  ]
  ```
- **Trade-offs**:
  - ✅ **Pros**: Secure by default, less boilerplate, centralized security logic
  - ❌ **Cons**: Must explicitly mark public routes, potential for confusion

### **Admin Role Management**
- **Decision**: Environment-based admin configuration (no RBAC database)
- **Why**:
  - Simple admin management via config (ADMIN_USER_IDS, ADMIN_EMAILS)
  - Appropriate for small team/single-tenant deployment
  - Fast lookups using Set data structure
- **Implementation**:
  - `@AdminOnly()` decorator marks admin-protected routes
  - Global `AdminGuard` checks user against admin lists
  - Applied to sensitive endpoints (health metrics, queue monitoring, security)
- **Trade-offs**:
  - ✅ **Pros**: Simple to configure, no database overhead, fast checks
  - ❌ **Cons**: Requires restart to update admins, no granular permissions, not suitable for multi-tenant

### **Health Endpoint Security Model** (Updated 2025-12-03)
- **Decision**: Tiered health monitoring (public basic status, admin-only detailed metrics including Prometheus)
- **Why**:
  - **Information Disclosure Prevention**: Internal metrics reveal infrastructure details (queue names, Redis status, error patterns)
  - **Attack Surface Reduction**: Prevents "register → get JWT → scrape metrics" attack vector
  - **Critical Discovery**: Initially made endpoints authenticated-only, discovered regular users could still access
  - **Final Solution**: `@AdminOnly()` decorator checking `ADMIN_USER_IDS`/`ADMIN_EMAILS` environment variables
  - **Monitoring Support**: Public endpoint (`/health`) still available for uptime monitors
- **Implementation**:
  - `GET /health` - Public, returns only "operational" or "down" (safe for external monitoring)
  - `GET /health/detailed` - `@AdminOnly()`, comprehensive health check (database, cache, performance)
  - `GET /health/queues` - `@AdminOnly()`, BullMQ queue health and Redis status
  - `GET /health/cache-metrics` - `@AdminOnly()`, cache statistics for monitoring
  - `GET /health/metrics` - `@AdminOnly()`, Prometheus text format metrics
- **Prometheus Integration**:
  - Use API key with `'admin'` or `'full'` scope for Prometheus scraper
  - Configure via `Authorization` header or `X-API-Key` in `prometheus.yml`
  - AdminGuard allows both JWT (human admins) and API key (Prometheus) authentication
- **Trade-offs**:
  - ✅ **Pros**: Secure by default, prevents infrastructure enumeration, protects against reconnaissance attacks
  - ❌ **Cons**: Prometheus requires API key setup, external monitors see only basic status
- **Security Impact**: Prevents attackers from registering free accounts to continuously scrape system internals

### **Email Verification System**
- **Decision**: Token-based email verification with expiration
- **Why**:
  - Prevent fake account creation
  - Ensure valid contact information
  - Security best practice for authentication systems
- **Implementation**:
  - Time-limited verification tokens (configurable expiration)
  - Token invalidation after use
  - Rate-limited verification request endpoint
- **Trade-offs**:
  - ✅ **Pros**: Validates user emails, prevents abuse, standard security practice
  - ❌ **Cons**: Requires email service configuration, additional complexity

## 🗄️ Database Architecture Decisions

### **SQLite vs PostgreSQL**
- **Decision**: Start with SQLite, plan migration to PostgreSQL
- **Why**: 
  - **Development**: Faster setup, no server configuration
  - **Production**: SQLite sufficient for current scale (up to 50k transactions/wallet)
  - **Future**: PostgreSQL when concurrency or size limits are hit
- **Trade-offs**:
  - ✅ **SQLite Pros**: Zero-config, single file, great for development
  - ❌ **SQLite Cons**: Limited concurrency, no advanced features
  - ✅ **PostgreSQL Pros**: Enterprise features, better concurrency, advanced indexing
  - ❌ **PostgreSQL Cons**: Setup complexity, resource requirements

### **Prisma ORM Choice**
- **Decision**: Use Prisma instead of raw SQL or other ORMs
- **Why**:
  - **Type Safety**: Generated types from schema
  - **Migration System**: Version-controlled database changes
  - **Query Builder**: Type-safe database operations
- **Trade-offs**:
  - ✅ **Pros**: Excellent TypeScript integration, great developer experience
  - ❌ **Cons**: Learning curve, potential performance overhead for complex queries

### **Database Schema Design**
- **Decision**: Normalized schema with clear relationships
- **Why**: 
  - **Data Integrity**: Prevents duplication and inconsistencies
  - **Query Efficiency**: Optimized for common access patterns
  - **Scalability**: Easier to add new analysis types
- **Trade-offs**:
  - ✅ **Pros**: Clean data model, efficient storage
  - ❌ **Cons**: More complex queries, potential for N+1 problems

## 🔄 Job Queue Architecture

### **BullMQ + Redis Choice**
- **Decision**: Use BullMQ with Redis for background job processing
- **Why**:
  - **Reliability**: Redis persistence, job retry mechanisms
  - **Scalability**: Multiple workers, queue prioritization
  - **Monitoring**: Built-in job progress tracking
- **Trade-offs**:
  - ✅ **Pros**: Production-ready, excellent TypeScript support
  - ❌ **Cons**: Additional infrastructure dependency (Redis)

### **Queue Design Strategy**
- **Decision**: Separate queues by operation type
- **Why**:
  - **Resource Management**: Different job types have different resource needs
  - **Priority Handling**: Critical operations can be prioritized
  - **Worker Specialization**: Workers can be optimized for specific job types
- **Trade-offs**:
  - ✅ **Pros**: Better resource utilization, easier monitoring
  - ❌ **Cons**: More complex infrastructure, potential for queue imbalance

## 💾 Caching Architecture

### **Two-Tier Cache for Holder Profiles**
- **Decision**: Implement Redis (Tier 1) + PostgreSQL (Tier 2) caching strategy
- **Why**:
  - **Progressive Streaming**: Enable instant partial results (serve 7 cached, compute 3 stale)
  - **Memory Efficiency**: Redis handles hot cache (1h TTL), PostgreSQL persists long-term
  - **Resilience**: Survive Redis restarts without full recomputation
- **Implementation**: `HolderProfilesCacheService`
  - Tier 1: `getTokenResult()`, `cacheTokenResult()` (Redis)
  - Tier 2: `getTokenSnapshots()`, `saveSnapshot()`, `hydrateSnapshot()` (PostgreSQL)
- **Trade-offs**:
  - ✅ **Pros**:
    - <50ms response for Tier 1 hits (same query within 1 hour)
    - ~100-200ms for Tier 2 hits (7 of 10 wallets cached)
    - Progressive UX: Users see data immediately, not after 30 seconds
  - ❌ **Cons**:
    - Two storage systems to manage
    - Tier 2 grows indefinitely (needs cleanup job)
    - Freshness logic complexity (snapshot.computedAt vs wallet.lastSuccessfulFetchTimestamp)

### **Smart Freshness Check**
- **Decision**: Use wallet sync timestamp instead of time-based TTL
- **Why**:
  - Snapshot from 8 hours ago is still fresh if wallet hasn't synced since
  - Avoids unnecessary recomputation for unchanged wallets
  - Only recompute when underlying data changes
- **Trade-offs**:
  - ✅ **Pros**: Efficient reuse of expensive analysis (270-line profile computation)
  - ❌ **Cons**: Requires tracking wallet.lastSuccessfulFetchTimestamp

### **Service Delegation Pattern**
- **Decision**: Cache service handles ALL caching logic (Tier 1 + Tier 2)
- **Why**: Follows existing patterns (PnlAnalysisService, BehaviorService delegate to core)
- **Trade-offs**:
  - ✅ **Pros**: Clean separation, processor stays thin (orchestration only)
  - ❌ **Cons**: Future need for dedicated HolderProfileAnalysisService (TODO)

## 🌐 API Architecture Decisions

### **NestJS Framework Choice**
- **Decision**: Use NestJS instead of Express or Fastify
- **Why**:
  - **Architecture**: Built-in support for modules, services, and dependency injection
  - **TypeScript**: First-class TypeScript support
  - **Ecosystem**: Rich middleware and plugin ecosystem
- **Trade-offs**:
  - ✅ **Pros**: Structured architecture, excellent documentation
  - ❌ **Cons**: Learning curve, opinionated design

### **REST vs GraphQL**
- **Decision**: REST API with structured endpoints
- **Why**:
  - **Simplicity**: Easier to implement and debug
  - **Caching**: Better HTTP caching support
  - **Tooling**: Excellent tooling for testing and documentation
- **Trade-offs**:
  - ✅ **REST Pros**: Simple, cacheable, tooling support
  - ❌ **REST Cons**: Over-fetching, under-fetching
  - ✅ **GraphQL Pros**: Flexible queries, single endpoint
  - ❌ **GraphQL Cons**: Complexity, caching challenges

### **JWT Refresh Token Strategy** (Added 2025-12-03)
- **Decision**: Rotating refresh tokens with replay detection and session management
- **Why**:
  - **Short-Lived Access Tokens**: 30-minute TTL reduces attack window
  - **Secure Refresh**: Refresh tokens hashed in Redis (hash → session mapping)
  - **Replay Protection**: Token reuse revokes entire session chain and triggers alerts
  - **Session Management**: Per-user session tracking for device management
- **Implementation**:
  - Access token: 30 min TTL (stateless JWT with `kid`, `iss`, `aud`, `nbf` claims)
  - Refresh token: 7-day sliding window stored hashed in Redis
  - Rotation: Each `/auth/refresh` issues new access + new refresh (old token revoked)
  - Per-user session sets: O(1) revocation, no full Redis scans
  - Absolute max lifetime: 7-day hard expiration for defense-in-depth
- **Trade-offs**:
  - ✅ **Pros**: Strong security (replay detection), better UX (refresh without re-login), session control
  - ❌ **Cons**: Redis dependency, more complex flow than simple API keys
- **Security Features**:
  - Password reset revokes all user sessions
  - Logout can target single session or all sessions (`/auth/logout-all`)
  - RefreshTokenService tracks device labels for user visibility

## 🎨 Frontend Architecture Decisions

### **Next.js App Router**
- **Decision**: Use Next.js 14 with App Router
- **Why**:
  - **Performance**: Built-in optimizations and server components
  - **Developer Experience**: Excellent TypeScript support and tooling
  - **Deployment**: Easy deployment to Vercel or other platforms
- **Trade-offs**:
  - ✅ **Pros**: Modern React features, great performance
  - ❌ **Cons**: Learning curve for App Router, newer technology

### **Component Library Strategy**
- **Decision**: shadcn/ui + Tremor for UI components
- **Why**:
  - **shadcn/ui**: Unstyled, accessible components that can be customized
  - **Tremor**: Specialized components for data visualization and metrics
  - **Consistency**: Both libraries follow similar design principles
- **Trade-offs**:
  - ✅ **Pros**: High-quality components, easy customization
  - ❌ **Cons**: Bundle size, dependency on external libraries

### **State Management Approach**
- **Decision**: SWR for server state, local state for UI
- **Why**:
  - **SWR**: Excellent caching, revalidation, and error handling
  - **Simplicity**: No complex state management libraries needed
  - **Performance**: Built-in optimizations for data fetching
- **Trade-offs**:
  - ✅ **Pros**: Simple, performant, great caching
  - ❌ **Cons**: Limited for complex client state

## 🔧 Analysis Engine Architecture

### **Service Layer Pattern**
- **Decision**: Separate business logic into service classes
- **Why**:
  - **Reusability**: Services can be used by CLI scripts, API, and workers
  - **Testability**: Easy to unit test business logic
  - **Maintainability**: Clear separation of concerns
- **Trade-offs**:
  - ✅ **Pros**: Clean architecture, easy to test
  - ❌ **Cons**: More files, potential for over-abstraction

### **Analyzer Classes Design**
- **Decision**: Separate analyzers for different analysis types
- **Why**:
  - **Single Responsibility**: Each analyzer has one clear purpose
  - **Testability**: Easy to test individual analysis logic
  - **Maintainability**: Changes to one analyzer don't affect others
- **Trade-offs**:
  - ✅ **Pros**: Clear separation, easy to extend
  - ❌ **Cons**: Potential for code duplication, more complex orchestration

## 📊 Data Processing Decisions

### **Batch Processing Strategy**
- **Decision**: Process transactions in configurable batches
- **Why**:
  - **Memory Management**: Prevents memory issues with large datasets
  - **Progress Tracking**: Users can see progress on long operations
  - **Error Recovery**: Failures don't lose all progress
- **Trade-offs**:
  - ✅ **Pros**: Better user experience, memory efficient
  - ❌ **Cons**: More complex logic, potential for partial failures

### **Caching Strategy**
- **Decision**: Minimal caching, focus on fresh data
- **Why**:
  - **Data Accuracy**: Blockchain data should be current
  - **Simplicity**: Easier to reason about data freshness
  - **Storage**: Avoids complex cache invalidation logic
- **Trade-offs**:
  - ✅ **Pros**: Always fresh data, simpler logic
  - ❌ **Cons**: More API calls, slower response times

## 🚀 Deployment Architecture

### **Self-Hosted Backend + Vercel Frontend**
- **Decision**: Backend on Raspberry Pi 5, frontend on Vercel
- **Why**:
  - **Cost**: Free hosting for frontend, minimal cost for backend
  - **Control**: Full control over backend infrastructure
  - **Performance**: Global CDN for frontend, local processing for backend
- **Trade-offs**:
  - ✅ **Pros**: Cost-effective, full control
  - ❌ **Cons**: Infrastructure management, potential reliability issues

### **PM2 Process Management**
- **Decision**: Use PM2 for Node.js process management
- **Why**:
  - **Reliability**: Automatic restarts, process monitoring
  - **Simplicity**: Easy to configure and manage
  - **Production Ready**: Battle-tested in production environments
- **Trade-offs**:
  - ✅ **Pros**: Reliable, easy to use
  - ❌ **Cons**: Additional dependency, learning curve

## 🔒 Authentication Architecture Summary (2025-12-03)

### **The Complete System**
```
┌─────────────────────────────────────────────────────────────────┐
│                     CompositeAuthGuard                          │
│                  (Global, tries JWT first)                      │
└──────────────────┬──────────────────┬───────────────────────────┘
                   │                  │
         ┌─────────▼─────────┐  ┌────▼──────────────┐
         │  JWT Auth Path    │  │ API Key Auth Path │
         │  (Human Users)    │  │ (Services/Legacy) │
         └─────────┬─────────┘  └────┬──────────────┘
                   │                  │
         ┌─────────▼─────────┐  ┌────▼──────────────┐
         │ Identity Only     │  │ Scoped Permissions│
         │ sub, email        │  │ read, admin, etc. │
         └─────────┬─────────┘  └────┬──────────────┘
                   │                  │
         ┌─────────▼─────────┐  ┌────▼──────────────┐
         │ AdminGuard Check  │  │ AdminGuard Check  │
         │ ADMIN_USER_IDS    │  │ + Scope Check     │
         └───────────────────┘  └───────────────────┘
```

### **Key Architectural Principles**
1. **Security by Default**: All routes protected unless marked `@Public()`
2. **Separation of Concerns**: Identity (JWT) ≠ Permissions (API keys)
3. **No Scopes in JWT**: Intentional - enables instant admin revocation
4. **Admin via Environment**: Simple config-based admin management (no RBAC tables)
5. **Health Endpoints Secured**: Prevents infrastructure enumeration attacks
